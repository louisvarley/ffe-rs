# Missions, the journal and the message pages

Status (2026-10-25): the BBS's contract offers are accepted, tracked and
settled; the port has a journal page and a comms page; and the source's
completion/rank/medal text is expanded from its own `0xff`-coded strings. The
civilian passenger, parcel and removal/assassination offers generated by the
merged Bulletin Board (`F638`/`F643`) are reachable, and so is the military
**package** offer from the 0x9827/0x9828 recruitment ads (`F493`/`F623`/
`F629-F632`). The military photo/bombing/assassination constructors still need
the military-base and target-ship state the port does not carry (see "Missing
data").

Source: `jjffe-master/ffe.asm`/`ffedat.asm`; the port is
`ffe_core::missions` (contract state, journal, pages), `ffe_rs::navigation::
mission_offer`/`military_offers`/`clear_post`, `ffe_rs::station::{Screen::
Journal, Screen::Comms, Screen::Military}` and the docked-screen wiring in
`main.rs`. No cache asset is added, so the cache version does not change.

## Contract fields and derived values

The contract is F290's five dwords:

```text
+0x00  reward           BBS row StrVars[0] (whole credits)
+0x04  basic_data       F638's `rand&7 | additive<<9 | package<<13`
+0x08  destination      StrVars[2], the `0x85ff` system code
+0x0c  deadline         F534: accept day + 0x1c; F632 military: +14..77
+0x10  name seed        StrVars[3] (F791's 0x92xx names)
```

`Mission` keeps those fields plus the source code, origin system/station name,
the passage/parcel text (`StrVars[1]`) or removal title (`StrVars[4]`), the
kind, and the status. The
reward is never recomputed: it is the BBS row's money slot, which the existing
`bulletin::ship_job`/`removal` generator already derived from
`DATA_006171..6174`/`DATA_006214`. The acceptance deadline is the source's
28-day rule; the removal ad's displayed date (`F643`'s `game day - 0x121cf7 +
7..70`) is not used as the contract deadline because F534 overwrites the
deadline slot when the contract is created.

Passenger/parcel encoding: `basic_data`'s low three bits are the passenger
count minus one, bit 13 marks the "small package" passage (0x991c, no cabins),
and bits 9..12 are the mission additive. `bulletin::ship_job` sets the fifth
`Var` to this word (it was previously always 0), so `missions::offer` can read
the count and the package flag without a second record. The port does not add
the FFED3D `ships` field (bits 16+), which is not in the DOS F638 word.

## Implemented actions

* **Accept** (`F534`): `State::accept` checks the 0x3b cap, appends the
  contract, writes the 0x992a page/journal entry and the comm message. `main`
  removes the advertisement (`F535`), posts the page to the console log
  (`F349`, `Cue::Message`) and beeps the row click (`F361`).
* **Complete** (`F303`): `State::settle` pays the whole-credit reward (the
  caller adds `reward*10` to the tenths cash field), raises `reputation` by one
  (cap 5), writes 0x9c31 (one passenger), 0x9c32 (a group), 0x9c33 (military
  delivery) or 0x9c34 (parcel/removal). A late arrival pays nothing and writes
  0x9c2c; a failure/expiry writes 0x9c29 (or F301's 0x9c36 for a passenger)
  and loses one reputation step.
* **Tick** (`F301`/`F302`): `State::tick(day, system)` completes an active
  contract whose destination is the current system and expires one past its
  deadline. `main` runs it each frame against the navigator's current system
  (not only when docked), reproducing F302's arrival check.
* **Abandon**: `State::abandon` writes 0x9c37 and loses a reputation step (the
  port's one-step equivalent of F485's `-8`).
* **Military package** (`F493`/`F623`/`F629-F632`/`F509`): selecting a
  recruitment ad opens `Screen::Military`. The list regenerates from a
  station/day stream; F629's 8 cargo variants are always offered, F630's 4 at
  more than 0x10 rank points and F631's 4 at more than 0x51. F632's decoded
  reward is `150/550/750 + 50*additive + 100*random(4)`, and its deadline is
  `day + 14 + random(0x40)`. Accepting uses F509's 0x2000/tier `basic_data`;
  completion uses F303's `seed==0` branch (0x9c33) and F306's rank page
  (song 7). A package delivery has no medal: F509's low bits are 0, so
  F303 picks `DATA_005115[0]`/`DATA_005116[0]` (0xff) and F307 is skipped.
  The offer taken today is filtered from the regenerated list (the source
  removes its `DATA_009004` slot).
* **Journal**: the source's `MISSION.DAT` journal archive is not in the cache;
  the port's journal records the contract events it can generate (accept,
  complete, fail/expire, abandon, military rank) with the source page text.
* **Comms**: `State::pages` holds the pages; the comms screen lists them newest
  first and `ReadPage` plays the page's source song (7 for F306's rank page, 10
  for F307's medal page) and marks it read.

## Journal and comms screens

`station::Screen::Journal` and `Screen::Comms` are port pages, not extra
station services (the original journal is the ship library's viewer F76/F78/F81
and the comms list is F343's). They use the 33-pixel paragraph layout, wrap at
312 pixels, have no row button and show the Go Back arrow (F566). `J` and `C`
open them while the station board has focus; they are called out as port
conveniences in the report. The status/cargo line is omitted on these pages so
the text has the full panel. The title for the journal is the source's
`SHIP LIBRARY ARCHIVES` (DATA_002304); the comms page is `Communications`.
`Screen::Military` is the 0x9827/0x9828 recruitment ads' target: the BBS
33-pixel layout with its row button, command text at x 140, and Go Back to the
bulletin board (F493's "Return to Mission List" is 0x9860).

## Persistence

`Flight::missions` is a `#[serde(default)] ffe_core::missions::State`, so a
save from before this slice loads with no contracts, journal or pages. The
state validates its bounds in `Flight::validate` (the 0x3b acceptance cap,
256 journal entries, 64 pages, reputation 0..5, rank 0..8, string lengths).

## Evidence

`cargo test -p ffe-rs --test station_view mission_offer_journal_and_comms_frames
-- --ignored` with `FFE_WORLD_CACHE` and `FFE_SHOT_DIR` writes
`MissionOffer-ours.ppm`, `Journal-ours.ppm`, `Comms-ours.ppm`,
`Military-ours.ppm` and `Comms-rank.ppm`; the frames in
`docs/evidence/missions/` are that run (320x200, palette applied). The test
also asserts the generated contract's destination and reward are non-empty,
that the journal/comms titles replace the cabin pixels, that the military row
is F632's 0x9854 text, that the rank page is F306's 0x9c39 text with the new
rank name, and that the frame is the real cache's Mars High board.

`cargo test -p ffe-rs --test missions` runs the scripted acceptance, arrival,
late-arrival, expiry and abandonment, the save round-trip and the old-save
default. `cargo test -p ffe-core missions` covers the source-field extraction,
the 0x992a/0x9c31/0x9c32/0x9c33/0x9c34/0x9c2c pages and the military rank page
plus the F307 medal path's song mapping. The cache-gated
`a_generated_bbs_post_becomes_a_contract` reads a real
generated post through `Navigator::mission_offer` and clears it with
`clear_post`.

## Missing data and owner decisions

1. **Military constructors.** The package constructor (F629/F630/F631/F632)
   and its list (F493) are ported; F632's constant `0xffe2091a` resolves to
   `-(50 * 0x996e) + 150`, giving the 150/550/750 base rewards (the full
   arithmetic is in `missions::military_offers`). The other F623 constructors
   (F625-F628: the military assassination, photography and bombing missions)
   need target ships and `DATA_ContractArray` military bases, which the port
   does not carry; they return no offer rather than inventing one. F496's
   detail page and its suggested-response conversation (0x9859..0x9868) are
   also not drawn: the port accepts the row directly and uses 0x992a's
   confirmation. Owner decision needed: port the base contract and detail
   pages, or keep the package list.
2. **Assassination/removal combat.** The contract pays on arrival at the target
   system (F303/F485's "people coming with us" is not modelled). F291's hostile
   spawn (`SpawnAssassins`, `DATA_005112`) is not wired, so an assassination is
   a delivery to the named system rather than a fight. F303's special
   `(basic_data & 0x1f) == 0x14` "Sorry, I can't pay at the moment" branch
   (0x9c35, the 0x99b4 removal title) is not detected because the port stores
   the removal title's text, not its code; removal settles with 0x9c34. This is
   reported, not faked.
3. **Cabins and the rank roll.** The port has no passenger-cabin count
   (`Status::cabins_total` is zero), so F534's "You do not have enough cabin
   space" check (0x9928) is not enforced. F521's `F922(9)` roll against
   `DATA_008922` (the "I don't deal with someone of your reputation" refusal,
   0x991e) is also not drawn, because the port accepts the row's offer directly;
   `missions::State::reputation` is kept and F303 raises/lowers it, but it does
   not gate acceptance yet. The contract still records the passenger count.
4. **Rank.** `military_points`/`rank` use `DATA_005114`'s thresholds. The
   nine names are the first nine Federal rank strings from `DATA_005104`'s
   0x9c4e..0x9c56 (Private..Captain); the Imperial ladder (0x9c5b..0x9c66) is
   not selected because the 20-byte contract has no allegiance field. The
   +500 points per delivery is the port's documented choice, not a source
   constant (F300's `pointGain` table is for the 52-byte military contracts).
   F306's promotion/demotion page is therefore always the current rank, not a
   before/after comparison.
5. **Journal archive.** `MISSION.DAT`'s offset/bit-permutation archive is not in
   the cache and is not parsed. The journal shows contract events only. If the
   owner wants the hand-coded news journal, the converter needs the
   `MISSION.DAT` bit-permutation (INVENTORY §3.3) and its 468-entry text table.
6. **Money unit.** The source's `DATA_008888` is in tenths; the port's
   `Flight::credits` is the same unit (`$100.0` is 1000). `missions::settle`
   returns whole credits and `main` multiplies by ten; the scripted test checks
   the conversion. If a future cash model changes the unit, this is the one
   conversion to update.
7. **Sound.** Accept/complete use F349/F351's `0x16` bong (`Cue::Message`);
   the row click is F361's `0x14` beep. Military package completion calls
   F306's song 7. F307's song 10 is wired for the medal-bearing military
   constructors, which are not ported (a package delivery's medal code is
   `0xff`, so F307 is skipped). No new sample or song asset is needed.
